# Аудит безопасности локального экземпляра

## Дополнение для установщика от 26.10.2026

- Из страницы входа убраны опубликованные демонстрационные логины и пароли; добавлен favicon из существующего логотипа. Локальный адрес PostgreSQL больше не показывается как адрес веб-сервера.
- В Git-файлы `database_import/` перенесены 39 связанных учебных записей и роли/пользователи. У пользователей нет пригодных паролей, они отключены; журнал аудита и конфигурация БД не экспортируются. Импорт разрешён только в пустую базу и выполняется одной транзакцией. Первый администратор получает новый случайный пароль.
- Bash-установщик не публикует `.env`, копии и первичные реквизиты. Доступ по сети требует TLS-сертификат; без него Nginx слушает только `127.0.0.1`. Обслуживающий процесс работает от `www-data`, приватные каталоги имеют права `700`, `.env` — `600`. Сборка статики доступна Nginx только для чтения.
- `pip-audit -r requirements.lock.txt` на 26.10.2026 не обнаружил известных уязвимостей. Проверены синтаксис трёх Bash-скриптов и 59 Django-тестов. Полный запуск установщика на целевой Linux-системе ещё не проводился.
- В локальном Windows-экземпляре прежние временные пароли остаются действующими, пока администратор их не сменит. Они исключены из фикстур и Git. Для ввода в эксплуатацию смените их и удалите `.runtime/initial-credentials.txt`.
- `check --deploy` в локальном HTTP-режиме выдаёт четыре предупреждения о HTTPS/HSTS и защищённых cookie. При `DJANGO_USE_HTTPS=1` остаются два предупреждения про HSTS для поддоменов и preload: эти параметры не включаются автоматически для произвольного домена/IP предприятия. Проверка фактической TLS-конфигурации проводится на целевом сервере.

Проверено 21.10.2026: исходный код Django, маршруты и права, импорт XLSX, резервное копирование, конфигурация, действующая PostgreSQL и установленные зависимости. Проведены регрессионные запросы через Django test client с включённой проверкой CSRF. Это проверка данного экземпляра, а не независимый пентест сети и ОС.

## Проверено без обнаруженной уязвимости в указанных сценариях

- Операции с резервными копиями требуют администратора; удаление и восстановление требуют CSRF. Имя файла сверяется с закрытым шаблоном, путь ограничен каталогом `.backups`. SQL-доступ и большинство бизнес-операций используют ORM или параметры запроса.
- Загрузка `.dump` ограничена размером и проверяется `pg_restore --list`; перед восстановлением создаётся страховочная копия. Экспортируемые Excel-ячейки с пользовательским текстом не интерпретируются как формулы.
- В шаблонах Django действует экранирование HTML; динамические значения старого интерфейса записываются через `textContent`, данные пользователя в bootstrap-скрипте экранируют символ `<`. Генератор PDF экранирует значения.
- Частные каталоги `.env`, `.pgadmin`, `.backups`, `.runtime` и `.pgdata` ограничены ACL Windows; у временного файла реквизитов проверены ACL владельца, Administrators и SYSTEM.
- 54 теста прошли, `node --check` не нашёл синтаксических ошибок, `makemigrations --check --dry-run` не нашёл пропущенных миграций.

## Оставшиеся ограничения перед сетевым выпуском

1. Локальный сервер слушает HTTP только на `127.0.0.1:8000`. `check --deploy` выдаёт 4 ожидаемых предупреждения про HTTPS, HSTS и Secure cookies. Для рабочих мест нужен TLS-прокси, ограничение прямого доступа к Waitress, корректные `ALLOWED_HOSTS` и доверенные источники CSRF, затем `DJANGO_USE_HTTPS=1`. Заголовок `X-Forwarded-Proto` должен устанавливаться только доверенным прокси.
2. Лимит входа хранится в памяти процесса и сбрасывается при перезапуске. Общий кэш и лимиты на уровне прокси обязательны для нескольких процессов и для защиты от распределённых попыток. Атакующий может временно заблокировать отдельный логин, исчерпав лимит.
3. Корень проекта наследует широкие права записи Windows. Частные файлы ограничены ACL, но пользователь, способный менять исходный код, может менять приложение. Сервис нужно запускать под отдельной учётной записью с правом чтения кода и записи только в необходимые каталоги.
4. Резервные копии содержат хеши паролей и рабочие данные. Для выноса с сервера нужны шифрование, отдельное хранилище и правила хранения. Временный файл `.runtime/initial-credentials.txt` следует удалить после передачи и смены паролей.
5. Строгая Content Security Policy не включена: сохранённый старый интерфейс содержит встроенный JavaScript. До сетевого выпуска нужно вынести его в отдельные файлы и включить CSP после проверки интерфейса.

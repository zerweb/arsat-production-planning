# АРСАТ — планирование и диспетчеризация производства

Веб-приложение на Django и PostgreSQL для учёта заказов и изделий, технологических маршрутов, производственных программ, заданий, материалов и фактического выполнения. Интерфейс предприятия сохранён.

## Возможности

| Раздел | Назначение |
| --- | --- |
| Заказы и изделия | Состав заказа, чертежи, сроки, статусы и история изменений |
| Технологические процессы | Связанные с изделиями операции, оборудование, нормы времени |
| Планирование | Годовая и квартальная программы, планы А и Б, расчёт загрузки |
| Производство | Задания, выпуск, контроль качества и отклонения |
| Материалы | Потребность, остатки, дефицит, импорт CSV/JSON/XLSX |
| Документы ЕСТД | Черновая маршрутная карта PDF по структуре ГОСТ 3.1118-82 |
| Администрирование | Пользователи и роли, проверка БД, SQL-копии и восстановление `.dump` |

Прямые интеграции с 1С, NX CAM и станками ЧПУ пока не включены. Маршрутная карта не заменяет утверждённый комплект ЕСТД.

Иконки сохранения и настроек: Font Awesome Free 6, © Fonticons, Inc., лицензия CC BY 4.0: https://fontawesome.com/license/free. SVG-файлы включены в проект и доступны без интернета.

## Учётные записи и права

В ТЗ на фото предусмотрены 13 рабочих мест: один начальник отдела, десять технологов и два инженера по нормированию. Тестовая загрузка создаёт для них отдельные учётные записи: `manager`, `user` и `technologist_02`–`technologist_10`, `normalizer_01`–`normalizer_02`. Дополнительные демонстрационные роли `admin`, `planner` и `supervisor` нужны для администрирования и других разделов приложения. Пользователи фикстуры изначально отключены и не имеют пригодных паролей; при установке выбранным тестовым пользователям задаются разные случайные пароли. В существующей базе новые рабочие места не активируются автоматически: администратор назначает их конкретным сотрудникам и задаёт индивидуальные пароли.

Технолог может создавать и изменять проект маршрута. Утверждение маршрута доступно только начальнику (`manager`) и администратору; изменение утверждённого маршрута технологом снимает утверждение. Инженер по нормированию работает с расчётом норм и справочником режимов резания. Права проверяются сервером, включая прямые обращения к API. Отметка утверждения и запись аудита пока не являются юридически значимой электронной подписью.

## Требования к серверу

- Debian, Ubuntu или Astra Linux с APT и systemd; права `sudo`, интерактивный терминал и Python 3.10 или новее.
- PostgreSQL можно установить на этом же сервере через меню, создать базу на работающем сервере или подключить существующую базу.
- Доступ к GitHub и пакетным репозиториям на время установки. Рекомендуется 2 ядра, 4 ГБ ОЗУ и 10 ГБ свободного места плюс пространство для резервных копий.
- Для доступа с других компьютеров откройте выбранный TCP-порт на хосте, а в облаке также во внешних правилах сети, например Azure NSG. Для автоматического сертификата нужны доступный из интернета TCP/80, выбранный порт HTTPS и DNS-запись домена или поддомена, указывающая на сервер.

Установщик предназначен для Linux. Локальная разработка проекта на Windows не проверяет развёртывание systemd/Nginx.

## Установка одной командой

На новом сервере в интерактивном терминале выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/zerweb/arsat-production-planning/main/bootstrap.sh | sudo bash
```

Скрипт скачает [репозиторий](https://github.com/zerweb/arsat-production-planning.git) в `/opt/avt` и запустит меню `install.sh`. Для уже установленного проекта та же команда загрузит актуальное меню обслуживания без изменения установленного кода. В меню выберите **4 — проверить и установить обновление** и подтвердите его. Меню также можно вызвать напрямую:

```bash
sudo bash /opt/avt/install.sh
```

При первой установке выберите **1 — новая установка**, режим доступа и порт сайта:

1. HTTP по IP или домену в локальной сети. Nginx слушает все сетевые интерфейсы, адрес имеет вид `http://IP:8080/`. Это режим по умолчанию.
2. HTTPS по IP или домену. Нужны готовые сертификат и ключ; браузер должен доверять сертификату.
3. HTTP только на сервере, адрес `http://127.0.0.1:8080/`.
4. Домен или поддомен с автоматическим сертификатом Let’s Encrypt. Укажите порт HTTPS (по умолчанию 443, можно выбрать 8880), DNS-имя и email. Nginx проверяет домен на порту 80 и перенаправляет HTTP на выбранный порт HTTPS. При выборе 8880 адрес имеет вид `https://имя-домена:8880/`. IP-адрес для этого режима не подходит.

Для режима 4 установщик ставит Certbot, запрашивает сертификат, включает системный `certbot.timer` или создаёт собственный таймер обновления и настраивает перезагрузку Nginx после обновления. Убедитесь, что DNS уже указывает на сервер и порт 80 вместе с выбранным HTTPS-портом открыты также во внешнем сетевом экране. Для порта 8880 откройте TCP/80 и TCP/8880. Во внутренней изолированной сети без доступа Let’s Encrypt используйте режим 2 с сертификатом корпоративного УЦ. Проверить обновление можно командой `sudo certbot renew --dry-run`.

**HTTP передаёт пароли и данные без шифрования.** Используйте сетевой HTTP только в доверенной закрытой сети; для публичного доступа выберите HTTPS. Внутренний процесс Waitress слушает только `127.0.0.1:8001`, поэтому внешний порт открывает Nginx.

### Подключение PostgreSQL

Установщик предложит выбор:

| Режим | Что требуется | Что делает установщик |
| --- | --- | --- |
| Создать новую БД | Логин и пароль администратора PostgreSQL с правом создать роль и БД; новые имена БД и роли | Проверяет подключение, создаёт отдельную роль со случайным паролем и пустую БД, применяет миграции |
| Подключить готовую БД | Имя существующей БД, пользователь приложения и пароль; права на создание таблиц | Проверяет подключение, применяет недостающие миграции, не удаляет существующие данные |
| Установить PostgreSQL здесь | Свободный порт `127.0.0.1:5432`; новые имена БД и роли | Ставит сервер PostgreSQL через APT, запускает службу, создаёт отдельные роль и базу со случайным паролем, применяет миграции |

В первом режиме администратор PostgreSQL должен иметь доступ к служебной базе `postgres` и право `CREATEROLE`/`CREATEDB` или быть суперпользователем. Имя новой базы и роли допускает строчные латинские буквы, цифры и `_`. Для внешнего сервера настройте его `listen_addresses`, `pg_hba.conf` и сетевой экран отдельно. Реквизиты приложения записываются в защищённый `.env`, исключённый из Git. Пароль администратора PostgreSQL не сохраняется.

При подключении готовой БД значения в квадратных скобках — текущие; Enter оставляет их без изменений. Для создания новой БД предлагаются имена `avt_production` и `avt_app`, даже если прежняя БД называлась иначе. Установщик не применяет миграции к непустой БД другого приложения без схемы АРСАТ. Если первая установка прервалась после импорта данных, повторный запуск распознает эти данные и завершит настройку пользователей и службы без повторного импорта.

После миграций можно выбрать загрузку демонстрационных данных. Импорт выполняется только в пустую прикладную БД. Он создаёт тестовые заказы, изделия, операции и пользователей. Установщик задаёт им новые случайные пароли; если активного суперпользователя нет, создаёт `admin`. **Логины и все вновь заданные пароли печатаются в терминале один раз.** Отдельный файл с паролями не создаётся. Пароли пользователей существующей БД нельзя извлечь из хешей; при необходимости воспользуйтесь сбросом ниже. Не записывайте терминальный вывод установки в общедоступные логи.

## Повторная настройка и сброс пароля

Запустите `sudo bash /opt/avt/install.sh`. Меню предлагает:

- **2 — изменить настройки:** IP/домен, порт, режим HTTP/HTTPS, автоматический сертификат, реквизиты PostgreSQL или всё вместе. Можно также установить локальный PostgreSQL. При смене БД установщик проверит подключение и применит миграции. Прежняя БД не удаляется. При ошибке конфигурационные файлы и служба возвращаются к прежним настройкам; операции миграции в выбранной БД не откатываются.
- **3 — сбросить пароль:** укажите существующий логин, в том числе `admin`; можно активировать отключённую запись. Случайный новый пароль записывается как Argon2-хеш в выбранную PostgreSQL и печатается только в терминале. Исходный пароль узнать невозможно.
- **4 — обновить проект:** установщик проверит Git и при наличии новой версии попросит подтверждение. Перед изменением кода он проверит зависимости и миграции и создаст архив PostgreSQL. Учётные записи, данные и `.env` сохраняются; тестовые данные повторно не импортируются.
- **5 — восстановить запуск службы:** проверяет права чтения файлов приложения, Django и доступность сайта, затем запускает службу. Настройки PostgreSQL и данные не заменяются.

Меняйте реквизиты БД только при наличии резервной копии. Во время перенастройки служба приложения кратковременно останавливается. После смены сетевого порта проверьте правила внешнего сетевого экрана; если доступ извне пропал, проверьте `sudo ss -ltnp`, `sudo nginx -t`, `sudo systemctl status avt` и `sudo journalctl -u avt -n 100 --no-pager`.

В администрировании раздел «Безопасность» позволяет включить изменение собственного логина и пароля для всех пользователей. По умолчанию оба изменения запрещены; администратор при необходимости задаёт пароль через управление учётной записью или меню сервера. Технический режим включается отдельной кнопкой и временно ограничивает доступ остальных пользователей. Настройки сервера и резервные копии находятся на вкладке «Сервер и копии».

При установке и обновлении исправляются только две известные повреждённые тестовые подписи `normalizer_01` и `normalizer_02`, если они до сих пор состоят из вопросительных знаков и совпадают с исходной фикстурой. Настоящие имена сотрудников команда не изменяет.

## Проверка работы

```bash
sudo systemctl status avt
sudo nginx -t
curl http://127.0.0.1:8080/health/ready/
sudo bash -c 'cd /opt/avt && .venv/bin/python manage.py check --database default'
```

Для HTTPS с готовым сертификатом используйте `https://IP:ПОРТ/health/ready/`, а с автоматическим сертификатом — `https://ДОМЕН:ПОРТ/health/ready/` (порт 443 можно не указывать). Проверка готовности должна вернуть `{"ok": true}`. Если локальная проверка работает, а браузер с другого компьютера не подключается, проверьте DNS, адрес сервера и внешние правила сети. Если выбран режим 3, внешний доступ намеренно выключен.

При HTTP команда `manage.py check --deploy` показывает предупреждения `security.W004`, `W008`, `W012` и `W016`: она проверяет настройки для HTTPS-развёртывания. Включение HTTPS-only cookies и принудительного SSL-перенаправления при HTTP нарушило бы вход. Поэтому установщик запускает обычную проверку Django; перечисленные предупреждения остаются при ручном `check --deploy` в HTTP-режиме. Для публичного сервера настройте HTTPS (режим 2 или 4) и повторите `check --deploy`.

Для резервного копирования версия `pg_dump` должна быть не ниже версии сервера PostgreSQL. Установщик проверяет версию сервера и при необходимости пытается установить соответствующий пакет клиента из настроенных APT-репозиториев. Например, для PostgreSQL 17 нужен `postgresql-client-17`. Если пакет не предлагается в Astra Linux, используйте совместимый репозиторий, разрешённый администратором системы. Приложение выбирает старшую установленную версию клиента в `/usr/lib/postgresql/`; при заданном `PG_BIN_DIR` используется указанный каталог.

## Импорт тестовых данных вручную

После миграций и **до создания любых пользователей и прикладных данных**:

```bash
cd /opt/avt
sudo -u www-data bash database_import/import.sh
```

Фикстуры `database_import/01_roles_users.json` и `02_sample_data.json` получены из тестовой PostgreSQL. В них нет пригодных для входа паролей. При ручном импорте администратору нужно отдельно задать пароль командой `provision_admin` через переменную `AVT_ADMIN_PASSWORD`, а обычным пользователям — через пункт 3 меню. Для первой установки удобнее ответить `y` на вопрос об импорте: установщик сделает это сам и покажет все новые пароли.

## Обновление и резервные копии

Сохраните копию PostgreSQL вне сервера. В интерфейсе администрирования доступны SQL-копии для просмотра, архив `.dump` для восстановления размером до 50 МБ и удаление старых копий. Более крупные архивы восстанавливайте средствами PostgreSQL в окно обслуживания. Для обновления запустите:

```bash
curl -fsSL https://raw.githubusercontent.com/zerweb/arsat-production-planning/main/bootstrap.sh | sudo bash
```

Выберите пункт 4 и подтвердите обновление. Установщик останавливает приложение на время резервного копирования и применения миграций, затем проверяет его запуск. Копия создаётся в `.backups` и доступна администратору. Новые таблицы, поля и индексы могут быть добавлены; миграции с удалением, переименованием, изменением существующих полей или произвольным SQL/Python автоматически блокируются и требуют отдельной проверки. Если ошибка возникла после начала миграций, проверьте состояние службы и журнал, а копию базы сохраните вне сервера. Автоматическое восстановление базы не выполняется. При локальных изменениях файлов или расхождении веток автоматическое обновление останавливается.

Локальные `.env`, `.runtime/`, `.backups/`, `.venv/` и `staticfiles/` исключены из Git. Полное развёртывание на целевом Linux-сервере и восстановление копии нужно проверить перед промышленным вводом.
